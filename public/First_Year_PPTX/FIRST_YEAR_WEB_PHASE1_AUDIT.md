## G. Existing Animation Technology Audit

### Existing animation technologies

- CSS keyframes and transitions are used heavily across subject decks and shared styles.
- SVG-based animation is common, including SMIL `animate` and `animateMotion` in world and scene components.
- React state, hooks, and the `cinematic` runtime provide slide lifecycle, motion budgets, performance checks, reduced-motion handling, and QA semantics.
- `requestAnimationFrame` is present in `src/cinematic/perf.js` for performance sampling.
- Canvas/WebGL/Three.js/Framer Motion/GSAP/React Spring are not installed or used in the audited dependency stack.

### Strengths

- Strong existing SVG/CSS vocabulary for projection-safe teaching scenes.
- Reduced-motion handling is already considered in several visual systems.
- A living presentation runtime exists, so Phase 2 can standardize engines without replacing navigation.

### Limitations

- Visual systems are mostly subject-specific; math, labs, CAD, circuits and programming need reusable first-year APIs.
- No symbolic math renderer or plotting engine is present.
- No general circuit simulation, code-execution trace, or experiment procedure engine exists.

### What should be reused

- Reuse `cinematic`, `CourseLanding`, subject kit patterns, typography/density/overflow utilities, and SVG/CSS animation conventions.

### What may need to be added in Phase 2

- A small graphing/equation rendering dependency may be justified; a circuit drawing/simulation library should be evaluated only if it saves substantial E/ECE lab and theory work. Do not add Three.js unless a genuine 3D teaching requirement emerges.

## L. Build Risks

### Visual risks

- The generated 9-slide-per-module PPTX pattern often uses concise teaching frames; direct conversion could create tiny central diagrams surrounded by unused space. Later phases should use full-stage diagrams and keep labels near the thing being explained.
- Math and code subjects can collapse into small formula/code blocks. Later phases should reserve large board/canvas zones, progressive reveals, and minimum projection-readable type.
- CAD/mechanics/physics slides are vulnerable to cornered drawings and decorative headers overpowering the teaching visual. Later phases should make the diagram the slide, not a thumbnail beside notes.
- Repeated card grids are already common in the app style. Later phases should use cards only for repeated items, not as the default explanation layout.

### Architectural risks

- Existing web subjects are self-contained. Reusing their patterns without a Phase 2 foundation will duplicate visual code across 50 subjects.
- Similar subject names across streams can tempt merging. Preserve VTU course identity and share only components.

### Pedagogical risks

- Several PPTX families can become definition-to-definition or formula-to-formula sequences. Later builds should organize modules as problem, model, worked example, misconception, practice.
- Labs should not become static manuals. They need procedure, observation, result and viva states.
- Humanities/communication subjects should avoid forced technical animation; scenarios and decision flows are better teaching vehicles.
